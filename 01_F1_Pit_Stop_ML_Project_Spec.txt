PRINCIPIO DE EJECUCION
======================
Este documento NO es una lista de tecnologias que deban aparecer a la fuerza.
Cada herramienta se incorpora solo si resuelve un problema verificable.

Reglas obligatorias:
1. No comenzar por AutoGluon, tuning ni ensembles.
2. No comenzar por MLflow antes de tener una ejecucion local minima que funcione.
3. No añadir una herramienta si no existe una pregunta experimental que justifique su uso.
4. No introducir MLOps completo: no Kubernetes, Airflow, serving, monitoring, feature store, CI/CD de modelos ni cloud obligatoria.
5. Los notebooks son para exploracion y comunicacion; la logica reusable debe terminar en src/.
6. Cada etapa tiene un criterio de salida. Si no se cumple, NO se avanza.
7. Se conserva un holdout final que no se usa para tomar decisiones de modelado.
8. Kaggle leaderboard es una comprobacion externa, no el mecanismo principal de seleccion.
9. Antes de fijar versiones, se realiza un smoke test conjunto de dependencias y luego se genera el lockfile.
10. Toda afirmacion de mejora debe estar respaldada por validacion reproducible, no por una unica corrida.

ADVERTENCIAS DE COMPATIBILIDAD
==============================
- skore esta en desarrollo activo: fijar la version que pase el smoke test y no actualizar durante el proyecto sin una rama de mantenimiento.
- skops no puede persistir cualquier funcion Python arbitraria. Evitar FunctionTransformer con funciones locales/lambdas dentro del pipeline final que se quiera serializar.
- AutoGluon persiste su TabularPredictor con su propio mecanismo; no intentar guardarlo con skops.
- MLflow y skore tienen areas que se solapan en almacenamiento/seguimiento. En estos proyectos:
  * skore = evaluacion, diagnostico y reportes.
  * MLflow = historial transversal de runs, parametros, metricas y artefactos.
  No duplicar todo automaticamente.
- El lockfile final es parte del entregable.
- **Incompatibilidad conocida**: AutoGluon puede requerir versiones antiguas de scikit-learn, mientras que skrub/skore necesitan las modernas. Si el smoke test falla, documentar y separar entornos (ver nota al inicio).


PROYECTO 1 — F1 PIT STOP PREDICTION
===================================

1. PROBLEMA
-----------
Competicion: Kaggle Playground Series S6E5 — Predicting F1 Pit Stops.
Objetivo oficial: predecir la probabilidad de que un piloto entre a pits en la siguiente vuelta.
Target: PitNextLap.
Metrica Kaggle: ROC-AUC.
Dataset Kaggle: train.csv, test.csv, sample_submission.csv; el dataset publicado contiene 33 columnas.
El dataset es sintetico y esta inspirado en un dataset real de estrategia de F1. Kaggle permite estudiar/incorporar el dataset original.

Pregunta de portafolio:
"How much does a carefully designed, leakage-aware ML pipeline gain or lose against AutoML, and what is the cost in complexity, compute and interpretability?"

Este proyecto NO tiene como meta ganar la competicion.
Tiene como meta demostrar:
- diseno correcto de validacion;
- deteccion de leakage;
- feature engineering temporal/contextual;
- comparacion justa manual ML vs AutoML;
- evaluacion reproducible;
- registro de experimentos;
- persistencia apropiada del modelo final.

2. HIPOTESIS
------------
H1. Una validacion aleatoria ingenua puede producir una estimacion demasiado optimista si filas relacionadas con una misma carrera/entidad aparecen en train y validation.
H2. Feature engineering causalmente valido, construido solo con informacion disponible hasta la vuelta actual, mejora al menos a algunos modelos manuales.
H3. AutoGluon puede superar a un modelo manual individual, pero no necesariamente ofrece la mejor relacion calidad/tiempo/latencia/complejidad.
H4. La diferencia entre datos sinteticos y datos F1 originales puede ser suficientemente grande para que mezclar datos sin analizar distribucion perjudique la generalizacion.

3. FUERA DE ALCANCE
-------------------
- simulador completo de carrera;
- reinforcement learning;
- prediccion de estrategia multi-vuelta;
- API de produccion;
- Docker obligatorio;
- cloud obligatorio;
- streaming;
- telemetria en tiempo real;
- MLOps end-to-end.

8. FASE 3 — VALIDACION Y LEAKAGE
--------------------------------
Esta es la fase central.

Archivo: src/f1pitstop/data/split.py

Primero identificar las unidades de dependencia reales disponibles en el dataset.
No asumir nombres: inspeccionar si existen race, driver, season, event, lap u otras columnas equivalentes.

Comparar como MINIMO:
V0 = StratifiedKFold aleatorio reproducible.
V1 = estrategia group-aware si existe un identificador de evento/carrera adecuado.
V2 = holdout temporal o por eventos posteriores si la estructura temporal lo permite.

Regla:
el holdout final queda congelado antes del tuning.

Test obligatorio:
tests/test_split.py debe verificar que los grupos protegidos no se solapan cuando la estrategia seleccionada asi lo exige.

Analisis de leakage:
para cada feature engineered responder:
- ¿se conoce en el instante t?
- ¿usa t+1 o futuro?
- ¿usa target directa o indirectamente?
- ¿usa agregados calculados con validation/test?
- ¿usa estadisticas globales que deben computarse dentro de cada fold?

Resultado esperado:
elegir UNA estrategia oficial de CV y justificarla en README.
La estrategia mas "dificil" no es automaticamente mejor; debe corresponder al uso que se afirma simular.

Criterio de salida:

11. FASE 6 — FEATURE ENGINEERING F1
-----------------------------------
Archivo: features/temporal.py y build.py.

Crear features SOLO si las columnas de origen existen y la semantica es comprobable.

Familias candidatas:
- progreso de carrera;
- vueltas restantes;
- edad del stint;
- proxies de degradacion de neumatico;
- delta de tiempo de vuelta respecto a referencias historicas disponibles;
- rolling statistics causales: shift(1) antes de rolling;
- cambios de posicion;
- interacciones compuesto x circuito/race;
- caracteristicas relativas al piloto calculadas sin mirar el futuro.

Regla de oro para rolling:
la fila t no puede usar informacion posterior a t; si la variable a predecir es t+1, revisar cuidadosamente si t es admisible.

**Ejemplo concreto y test asociado:**
Supongamos que tenemos una columna `lap_time` y queremos una rolling mean de los ultimos 3 tiempos.
Para predecir `PitNextLap` en la vuelta `t+1`, la feature para la fila `t` debe usar `lap_time` de `t-1`, `t-2`, `t-3` (es decir, `shift(1)` antes de `rolling`).
En el test `test_features.py` se incluira un DataFrame artificial con 5 vueltas y se comprobara que el valor calculado para la vuelta 3 no incluye `lap_time` de la vuelta 4 ni 5.

Experimentos:
E10_raw_features
E11_basic_domain_features
E12_temporal_features
E13_full_leakage_safe_features

Cada nueva familia entra mediante ablation:
base + una familia a la vez.
No mezclar 40 nuevas variables y atribuir la mejora a "feature engineering".

Tests:
- mismas filas antes/despues salvo transformacion documentada;
- no NaN inesperados infinitos;
- orden temporal conservado cuando aplique;
- rolling no accede al futuro en un dataset toy controlado.

14. FASE 9 — SKORE
------------------
Usarlo despues de tener candidatos serios.

Funciones objetivo:
- evaluate() con el splitter oficial cuando el estimador es compatible;
- ComparisonReport para varios candidatos sklearn;
- metricas y curvas;
- timings;
- permutation importance cuando sea interpretable/viable;

**Advertencia practica:**
Si `skrub.tabular_pipeline` no es completamente compatible con `skore.evaluate()` (por ejemplo, falla la inspeccion interna), no se debe forzar. En ese caso, se evalua el pipeline con `cross_validate` de sklearn y se usan las metricas calculadas; `skore` se limita a generar los reportes visuales (ROC, PR, etc.) a partir de las predicciones guardadas.
La decision de no usar skore para ese estimador se documenta como una limitacion tecnica, no como un fracaso.

Reportes minimos:
- CV summary;
- ROC curve;
- precision-recall curve;
- calibration curve si aporta informacion;
- confusion matrix a un umbral documentado solo para analisis;
- permutation importance del finalista sklearn (si el estimador lo permite).

22. DEFINITION OF DONE
----------------------
El proyecto esta terminado cuando:
[ ] entorno reproducible + lockfile (o documentacion de multiples entornos);
[ ] raw data no modificado;
[ ] data audit;
[ ] EDA orientado a preguntas;
[ ] validacion defendible y testada;
[ ] leakage analysis explicito;
[ ] Dummy + modelo simple;
[ ] al menos una comparacion honesta de skrub;
[ ] feature engineering con ablaciones;
[ ] maximo 2 familias seriamente tuneadas;
[ ] AutoGluon challenger con presupuesto limitado;
[ ] skore aplicado a candidatos compatibles (con las adaptaciones documentadas);
[ ] MLflow contiene los runs clave;
[ ] modelo sklearn final validado con skops;
[ ] holdout final intacto hasta el momento acordado;
[ ] submission reproducible;
[ ] tests pasan;
[ ] README explica decisiones negativas, no solo tecnologias usadas.

23. STOP CONDITIONS
-------------------
Detener sofisticacion si:
- CV no es estable;
- existen dudas de leakage;
- un modelo simple ya alcanza el techo empirico (ej. AUC > 0.98 en el holdout);
- AutoGluon consume recursos sin ganancia material (ej. mejora < 0.001 en AUC);
- una feature no tiene explicacion o ablation;
- el siguiente paso solo sirve para "poner otra tecnologia en el CV".
